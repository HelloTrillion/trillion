# Skills

**Date:** 2026-10-23 · **Requirements:** CON-6 · **Respects:** CON-6a, SPN-6, BRN-6, BRN-11

A skill is a folder with a `SKILL.md`: a short header (name, description) and
instructions below it, sometimes with reference files and scripts beside it. Claude,
Codex and others read the same format. This slice lets Trillion use them: from a
small curated set we ship, and from folders the user chooses, such as an existing
`~/.claude/skills`.

A skill adds know-how, never power. Trillion has no tool that runs code, so a skill's
scripts are reference text she can read and never run. Whatever a skill leads her to
do goes through the spine like any other tool call.

## Decisions

| | Decision | Why |
|---|---|---|
| D1 | Skills come from **folders the user adds** plus a **curated set shipped in the package**. No public registry, no marketplace. | CON-6 says no marketplace in P0 or P1. The curated set gives a useful start; folders let people reuse the skills they already have. |
| D2 | **Scripts load but never run.** The card says so. | No code-execution tool exists, and adding one without a sandbox is Phase 2 (CON-6a). Reading them still helps her follow the skill. |
| D3 | **Every skill starts off.** The user turns each one on after seeing what it says it does. A skill whose files change switches back off. | A skill's instructions steer her. Only text the user approved, byte for byte, gets that standing. |
| D4 | **Index in the prompt, full text on demand** (`skill_open`, `skill_file`). | The format is built for it: names and descriptions are cheap, full instructions are loaded only when a task needs them. The prompt stays small and cache-stable. |

## What the user sees

**Settings → Skills**, beside Connected apps, in the same gallery style:

- **Curated:** the skills we ship, as cards with a switch.
- **Your folders:** "Add a folder" takes a path. Every skill found in it is a card,
  switched off. A folder can be removed; its skills go with it.

Each card shows:

- the name and the description from the skill's header;
- the folder it came from (curated skills say "Included with Trillion");
- **tools it mentions:** its `allowed-tools`, matched to her tool names, with names
  she does not have shown as "not available in Trillion";
- **"Includes scripts Trillion won't run"** when the folder holds any script
  (`.py`, `.sh`, `.js`, `.ts`, `.rb`, `.ps1`, or a file marked executable);
- its state: **Off**, **On**, **Changed since you turned it on** (off, with a button
  to look again and turn it back on), or **Can't be used** with the reason.

## Where things live

- Curated skills: `src/trillion/skills/curated/<name>/SKILL.md`, shipped in the wheel.
- The user's choices: `~/.trillion/skills.json`, written whole (OPS-2):

  ```json
  {
    "folders": ["/Users/someone/.claude/skills"],
    "enabled": {
      "curated:email-replies": "sha256:…",
      "folder:/Users/someone/.claude/skills/pdf": "sha256:…"
    }
  }
  ```

  The key is the skill's **id**: `curated:<name>`, or `folder:<absolute path of the
  skill's folder>`. The value is the fingerprint the user approved.

## Pieces

### `skills/parse.py`: reading one skill

`parse(folder) -> Skill | Invalid`.

- The header is the YAML block between the first two `---` lines. Read with
  `yaml.safe_load`; it must be a mapping. PyYAML is already installed through other
  packages; this slice makes it a direct dependency.
- `name`: required; lowercase letters, digits and hyphens; 1–64 characters; no
  leading, trailing or doubled hyphen.
- `description`: required; 1–1,024 characters after trimming and joining its lines.
- `allowed-tools`: optional; a string (space- or comma-separated) or a list of
  strings. Kept as written.
- `license`: optional; shown on the card when present. A value that is not text is
  ignored.
- Other header fields are ignored.
- Limits: `SKILL.md` up to 64 KB; any one file up to 256 KB; at most 200 files, 200
  folders and 8 levels of folders (a folder deeper than that counts even when empty).
  Files past a limit make the skill **invalid**, not partly loaded. Reading stops at
  the first limit passed, so a large folder added by mistake is never read to the end.
- Text must be UTF-8. A file that is not (an image, a PDF) is listed but `skill_file`
  will not return it.

`Invalid` carries a reason in plain words ("its header has no description"). An
invalid skill is a card, never an exception.

### `skills/fingerprint.py`

`fingerprint(folder) -> str`: SHA-256 over every file's path relative to the folder
and its bytes, in sorted path order, prefixed `sha256:`. Symlinks are not followed;
a symlink's target path is hashed as its content, so retargeting one changes the
fingerprint.

### `skills/library.py`: finding skills and their state

`Library(settings_path, curated_root, *, data_root)`:

- `scan() -> list[Entry]`. For the curated root and each user folder: the folder
  itself if it has a `SKILL.md`, otherwise each direct subfolder that has one. Not
  deeper. Each `Entry` has the id, the source, the parsed skill or the reason it is
  invalid, its fingerprint, and its state:
  - **off:** not in `enabled`;
  - **on:** in `enabled` with the same fingerprint;
  - **changed:** in `enabled` with a different fingerprint, which counts as off;
  - **invalid:** cannot be parsed or breaks a limit, which counts as off.
- `enabled() -> list[Entry]`: the **on** entries, sorted by name, then id.
- `turn_on(id, expected=None)` records the current fingerprint; `expected` is the
  fingerprint the card showed, and if the files changed since, it refuses ("that skill
  changed since this page showed it; look again"). `turn_off(id)` removes it.
- Each skill is read between two fingerprints; files changing meanwhile never count
  as **on**. An invalid skill is not fingerprinted. `enabled()` and `lookup()` read
  only the skills turned on; `scan()` reads them all.
- `add_folder(path)` accepts an existing directory, expands `~` and resolves it to an
  absolute path; a link (such as a dotfiles `~/.claude/skills`) is stored as the folder
  it points to. It refuses Trillion's own data folder or any folder holding it
  (compared as the same folder on disk, so case does not matter), and any filesystem
  root. The same folder is stored once; a stored folder later replaced by a link is
  reported as not found. `remove_folder(path)` also drops the enabled entries of that
  folder and its direct subfolders, except those another added folder still offers.
- Of a folder of skills, at most 500 direct subfolders are considered; linked
  subfolders are skipped. A folder that can't be listed contributes no skills.
- Missing folders are reported on the folder ("not found"), not dropped.

When two **on** skills share a name, the index lists both with the folder they came
from (the user's home folder written as `~`; the skill's own folder when both came
from the same one), and `skill_open` takes either the id or a name that is unique
among **on** skills. A name only a **changed** skill has finds it, so the tool can say
it changed.

### The two tools (`tools/skills.py`)

Both are `Risk.READ`, so they run without asking.

- **`skill_open(skill)`**: `skill` is a name or an id.
  - It looks the skill up among the **on** ones and recomputes its fingerprint.
  - On a mismatch it refuses ("that skill changed since it was turned on, so it is
    off until you look at it again in Settings → Skills") and the state becomes
    **changed**.
  - Otherwise it returns the instructions (the text after the header) and the list
    of the skill's other files, with sizes, scripts marked as scripts.
- **`skill_file(skill, path)`**: one file from an **on** skill, checked the same way.
  - `path` is relative to the skill's folder. It refuses absolute paths, `..`
    anywhere, anything that resolves outside the folder, symlinks, non-UTF-8 files
    and `SKILL.md` itself (use `skill_open`).
  - Scripts come back as text, with a first line that says Trillion does not run them.

**Trust.** What these tools return is approved by the user, byte for byte, so it is
not wrapped as untrusted (SPN-6). It is still a tool result: it can guide her, and it
cannot change a gate, because the gates are code. Anything she reads *while following*
a skill (a web page, an email) is untrusted as always.

### Her prompt (`persona/prompt.py`)

`system_blocks` gets a `skills` argument. When any skill is on, it adds
`prompts/skills.md` (when to open a skill, that scripts are never run) and the list:

```
- email-replies: Draft a reply to an email in the user's voice. …
- pdf (from ~/.claude/skills): Fill in and read PDF forms. …
```

There are at most 50 entries and about 6,000 characters. Past either limit, the list
stops and says how many more are on, and Settings shows the same warning. The block
is identical turn to turn until a skill is switched on or off, so the prompt cache
holds (BRN-11). `describe_self` lists the skills that are on (BRN-6).

### API (`api/skills.py`)

All routes are behind the session token, like every `/api/` route.

- `GET /api/skills`: folders (each with found/not found), and every entry: id,
  source, name, description, license, tools it mentions (each marked available or
  not), has-scripts, state, and the reason when invalid.
- `POST /api/skills/folders` `{path}` adds a folder; `DELETE /api/skills/folders`
  `{path}` removes one.
- `PATCH /api/skills` `{id, on, fingerprint?}`. The id travels in the body because it
  holds `:` and `/`. `fingerprint` is the one the card showed: turning on refuses if
  the files changed since. Turning on a **changed** skill records the new fingerprint:
  the user saw the card and chose again.

Each change rebuilds the system block and the registry's view on the next turn; no
restart is needed.

### Settings (`apps/web/src/skills.ts`)

A Skills section in Settings, reusing the gallery's cards, switches and state dots
from `connected.ts`. A folder field with the same paste-and-check feel as "Add your
own". The changed state links straight to its card (`#show=skill:<id>`).

### `trillion doctor`

One line, **Skills**: how many are on, plus any that are changed or invalid and any
folder not found (status `warn`, with the fix). Nothing on: `info`.

## Curated set

Three short skills we write ourselves, so licensing is ours. Each uses only tools
Trillion has:

- **email-replies**: draft a reply in the user's voice from the thread and their
  standing rules. Sending stays the gated `gmail_send`.
- **meeting-prep**: before an event, gather what she knows about it and the people
  attending from Calendar, Gmail and memory, and write a short brief.
- **weekly-review**: look back at the past week's calendar and memory and ahead to
  the next week, and suggest what to drop, move or prepare.

## Out of scope

- Running scripts (Phase 2, with a sandbox).
- Installing from a URL or a registry; updating skills.
- Skills for user-defined agents (AGT-1/2): later, using this library.
- Editing skills in the app.

## Testing

- **Parsing:** valid skills; a missing or non-mapping header; a missing description;
  bad names; size, file-count and depth limits; `allowed-tools` as a string and as a
  list; a real Claude-style skill folder with scripts and reference files.
- **Fingerprint and state:** editing, adding, removing or renaming a file, or
  retargeting a symlink, turns **on** into **changed**; turning it on again records
  the new fingerprint.
- **Library:** curated and folder discovery (the folder itself, and its direct
  subfolders); a missing folder; refusing the data folder and a filesystem root;
  removing a folder drops its enabled entries; duplicate names.
- **Tools:** `skill_open` refuses a skill that is off, changed or unknown;
  `skill_file` refuses `..`, absolute paths, escaping symlinks, `SKILL.md`, binary
  files and files of skills that are off; scripts come back as text marked not run.
- **Prompt:** the list appears only when a skill is on; it respects 50 entries and
  6,000 characters; the block is byte-identical across turns until a switch changes.
- **API and web:** each route, including a changed skill turned back on; the
  Skills panel renders every state.
- **End to end:** with a local model, she opens a turned-on skill when a request
  matches it and follows it; a skill that is off is never opened.
